## Magnification smoothness on 2026-10-18

Cause of the lag: the animation ran on a `DispatcherTimer` of 16 ms and every pointer event called `Start()` on it, which restarts a running timer, so while the pointer moved the timer never ticked; when it did tick it was every ~30 ms. It now steps once per frame (`CompositionTarget.Rendering`, by elapsed time, time constant 30 ms) and unsubscribes when the icons have settled. A temporary harness (not committed) drove the same code with a synthetic pointer on an icon (Magnification 1.45, Mode Floating, six items): time to reach 99 % of the target scale 435 ms before and 151 ms after; back to 1.0 372 ms before and 125 ms after; during a 600 ms sweep along the row the icon under the pointer was on average 70 % of its scale step behind the target before and 21 % after, and the old timer ticked zero times during the sweep. Real pointer input cannot be injected here, so the feel with a mouse is for the user to judge. Auto-hide sliding still uses a 16 ms `DispatcherTimer` (about 30 ms in practice) and was not changed.

Follow-up the same day, after the user reported the icons shaking while the pointer moves over them: the exit event of the icon row fired whenever the pointer crossed a gap that lies outside every item (above the shelf, between two enlarged icons; the gaps stay 8 px wide when icons are enlarged) and reset the icons for a frame or two before the next move event grew them again. The old slow timer hid it. Pointer events now come from the whole shelf (`DockSurface`), and an exit resets the icons only after 90 ms. A harness that fired an exit and an enter in a row (about 90 ms apart in practice, because `Task.Delay(1)` is coarse) showed the hovered icon dipping to 1.02 without the grace time and to 1.38 with it, target 1.45; real gap crossings last a few milliseconds. The cause is reasoned from the code and the harness, not seen with a real mouse.

## Frame loop on 2026-10-18

`Motion` and `FramePacer` (Core, 6 new tests, 138 in all) and `FrameLoop` (App) replace the per-animation subscriptions: magnification and the auto-hide slide run as steps of one `CompositionTarget.Rendering` subscription per dock window, which exists only while something moves. A temporary probe (not committed) counted, over 2 s on this machine (one display, 100 %): 402 raw `Rendering` events (about 200 Hz) and 201 paced steps, one every 10.0 ms on average (95th percentile 10.4 ms, longest 10.9 ms). The pacer skips frames that come within 6 ms of the last step and keeps their time, so the animation length does not change. CPU use was not measured.

`dock-features-check`, `displays-check`, `appbar-smoke` and `exit-smoke` pass. `autohide-smoke` failed once, on the first launch after a rebuild (the dock had not moved after 2 s), and then passed in 7 runs in a row, so that failure is not reproduced and its cause is unknown; the slide itself (hidden and revealed positions) is correct in those runs. What the slide and the magnification look like with a real pointer is for the user to judge.

## Working set and signing checks on 2026-10-18

Working set of the release build (default settings, Windows 11, one NVIDIA GPU, measured with `Win32_PerfFormattedData_PerfProc_Process`): idle 160 MB working set, of which only 38 MB is private; private bytes 100 MB. Most of the rest is shared images, chiefly the GPU driver (`nvgpucomp64.dll` 106 MB and `nvwgf2umx.dll` 86 MB of image size, loaded by Direct3D for composition) and the WinUI framework. Opening the app menu for the first time adds about 75 MB of private bytes (working set 250 MB), 20 more open/close cycles add about 25 MB, and then it stays flat (40 and 80 cycles within 2 MB of each other, handles flat); `EmptyWorkingSet` drops the working set to about 5 MB and it comes back to about 17 MB in seconds, which shows how much of it is resident but idle. The managed heap is only 2 MB after a forced collection, so the growth is native (the full-screen blurred menu surface, XAML and composition), not a managed leak. Tried and rejected: closing the menu window after 5 s idle (private bytes stay, a forced GC changes nothing) and the .NET settings `gcConcurrent=0`, `GCgen0size`, `GCConserveMemory` (no change or slightly worse). No cheap reduction exists; the ~290 MB seen earlier is the idle 160 MB plus the menu after use. A real cut would mean replacing the acrylic menu surface with a plain one, which is a design change.

Signing: `scripts/sign.ps1` (signtool from the Windows SDK) is used by `build-release.ps1` and `build-installer.ps1` when `-CertificateThumbprint` is given (the certificate must be in `Cert:\CurrentUser\My` with its private key; `-TimestampUrl` defaults to DigiCert's, pass `''` to sign offline). Tested with a throwaway self-signed code-signing certificate (created for the test and removed after): `FloatDock.App.exe`, `FloatDock.Core.dll`, `FloatDock.Windows.dll`, `Guardian\FloatDock.Guardian.exe` and `FloatDock-Setup-0.2.0.exe` carry the certificate's signature, third-party DLLs are untouched, the zip is made after signing. The status reads `UnknownError` because a self-signed certificate is not trusted; with a certificate from a certificate authority it must read `Valid`, and SmartScreen reputation is a separate matter that no script can check. Not tested: a real certificate, a timestamp server.
